# Задачи для shugarm: интеграция, тестирование и CI

**Ветка задачи:** `tasks/shugarm-next`  
**База:** `feature-waveform-adsr`, коммит `b3e2294`  
**Приоритет:** сначала надёжность и проверка текущего синтезатора, затем расширение функциональности.

## Контекст

Подключены MIDI, четыре формы волны, ADSR, master gain и APVTS со state save/load. Локальные Debug- и Release-тесты проходят. Fairchecker проверил Standalone с Arturia MiniLab 3: ноты играются, элементы APVTS работают. При одновременной игре соседних нот звук кажется слишком грязным — причина пока не установлена. Не считать проверенными сохранение в DAW, автоматизацию и поведение на разных системах без отдельной проверки.

## 1. CI: сборка и тесты на каждый PR

- [ ] Создать `.github/workflows/ci.yml`: запуск на pull request и push в `main`, с возможностью ручного запуска.
- [ ] Checkout с подмодулем JUCE (`submodules: recursive`).
- [ ] Матрица Linux, macOS, Windows; конфигурирование с `BUILD_TESTING=ON` и Release-сборка VST3, Standalone и `CresizerTests`.
- [ ] Запуск `ctest --test-dir build -C Release --output-on-failure`; использовать `--config Release` при сборке для multi-config генераторов.
- [ ] Установить необходимые Linux-зависимости JUCE, ориентируясь на `tasks/ci-cd.md` и фактический результат CI.
- [ ] Сохранить логи и, если сборка проходит, артефакты VST3/Standalone для каждой платформы. Не публиковать релиз автоматически на этом этапе.
- [ ] Обновить `tasks/ci-cd.md` по факту: что реализовано, что ещё не прошло и ссылки на запуски.

**Приёмка:** все три job реально прошли в GitHub Actions; тесты обнаружены CTest и выполняются, артефакты скачиваются. Если платформа недоступна или сборка падает — зафиксировать ошибку и не помечать её выполненной.

## 2. Интеграционные и регрессионные тесты

- [ ] Проверить через `CresizerAudioProcessor`: MIDI note-on даёт ненулевой конечный сигнал, note-off приводит к завершению release; проверить sample offset MIDI в блоке.
- [ ] Проверить влияние каждого параметра ADSR, gain и waveform на DSP, а не только значение атомика или диапазон. Отдельно проверить mute после завершения 20-мс сглаживания.
- [ ] Расширить round-trip состояния: все параметры, повреждённые данные и неверный корневой тип; убедиться, что состояние не заменяется некорректными данными.
- [ ] Проверить voice stealing и повторное нажатие одной ноты, несколько голосов, тишину до первой ноты и предел пиков на выходе.
- [ ] Тесты детерминированы и реально проверяют условия в Debug и Release, без зависимости от аудиоустройства или отображения окна.

**Приёмка:** новые проверки падают при намеренном нарушении проверяемого поведения; локально и в CI проходят в Release. Использовать CTest, команды и названия тестов описать в README или задаче.

## 3. Проверка в реальном хосте

- [ ] В доступной DAW загрузить VST3, проверить MIDI и аудиовыход; записать название/версию DAW, ОС и способ проверки.
- [ ] Проверить автоматизацию параметров и восстановление проекта/пресета после закрытия и открытия, включая waveform и ADSR.
- [ ] Проверить поведение на разумных размерах буфера и отсутствие зависших нот. Отдельно зафиксировать любые щелчки при смене параметров.
- [ ] Обновить статусы roadmap только для действительно проверенных пунктов. Недоступные DAW/платформы оставить открытыми.

**Приёмка:** короткий отчёт с результатами и шагами воспроизведения выявленных проблем. Не выдавать Standalone-тест за тест VST3 в DAW.

## Границы и взаимодействие

- Не менять существующие ID параметров: они используются в состояниях и автоматизации хоста.
- Не переделывать DSP и GUI параллельно с fairchecker без согласования. Базовый фильтр, эффекты и релизный pipeline — отдельные следующие задачи после стабилизации.
- Грязное звучание соседних нот передать fairchecker с условиями воспроизведения; не маскировать его изменением громкости или лимитера без измерений.
- Если `feature-waveform-adsr` ещё не в `main`, открывать PR этой ветки в `feature-waveform-adsr`; после объединения базы согласовать перенос PR в `main`.
